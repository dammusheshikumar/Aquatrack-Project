# AquaTrack Frontend (v2 — Figma design, wired to your backend)

This replaces the plain-CSS frontend with the design generated by your Figma AI workflow —
same animations, same Tailwind design system, same every page/tab/button — now connected to
the real AquaTrack Spring Boot API instead of mock data.

## What changed from the Figma export

The Figma output was a great-looking **prototype**: real components and animations, but every
page held its data in local mock arrays and faked network calls with `setTimeout`. To make it
a working app, I:

1. **Converted `.tsx` → `.jsx`.** Your original project spec said no TypeScript. I stripped
   type annotations, `interface`/`type` declarations, and generics — the JSX, class names,
   and animation logic are untouched.
2. **Kept Tailwind CSS and Vite**, even though neither was in the original spec. Rewriting
   ~2,500 lines of Tailwind utility classes into plain CSS would have meant redoing the design
   by hand and risking visual drift from what you approved. Vite is just the build tool; it
   doesn't change what ships to the browser. Flag it if you'd rather I redo this without them.
3. **Replaced local `useState`-based "page" switching with real routing** (`react-router-dom`).
   The original `App.tsx` just swapped which component rendered — no URLs, no browser
   back/forward, no ability to protect a route by role. Now `/`, `/login`, `/register`,
   `/resident/*`, `/admin/*` are real routes, and `/resident/*` and `/admin/*` are gated by a
   `ProtectedRoute` that checks the logged-in user's role against the JWT session.
4. **Extracted `Navbar` into its own file.** The original code imported it from two different
   paths (`'../components/ui'` in `Landing.tsx`, `'../components/Navbar'` elsewhere) — only one
   of which existed. I formalized it as `components/Navbar.jsx`, and it now reads the logged-in
   user straight from auth context instead of needing props threaded through every page.
5. **Wired every page to your real API** — see the full endpoint map below. Every mock array,
   fake `setTimeout("success")`, and canned "3 pending approvals" badge is now a real
   `axios` call against your Spring Boot backend, with real loading states (using the existing
   `.skeleton` shimmer style from your CSS — I only added a small `SkeletonRows` component,
   no new visual language) and real error banners using your existing `AlertBanner` component.
6. **Real Google Sign-In.** The Figma login page had a nicely-styled fake Google button that
   just faked a delay. It's now Google's own rendered button (Google Identity Services),
   verified server-side, wired to your existing `/auth/google/login` and
   `/auth/google/register` endpoints and the pending-approval flow.
7. **Fixed a couple of real bugs** carried over from the generated code: keyed list items were
   using bare `<>...</>` fragments instead of `<Fragment key={...}>` in two tables (React
   silently warns and can misbehave on reorders/updates with this pattern) — fixed without
   touching the visual output.

## Running it

```bash
cd aquatrack-frontend
npm install
cp .env.example .env      # set VITE_API_BASE_URL and VITE_GOOGLE_CLIENT_ID
npm run dev
```

Runs on `http://localhost:3000` by default (configured in `vite.config.js`) and expects your
Spring Boot backend at `http://localhost:8080/api` (override via `VITE_API_BASE_URL`).

**Google Sign-In** needs a real OAuth Client ID from the
[Google Cloud Console](https://console.cloud.google.com/apis/credentials), with
`http://localhost:3000` added as an authorized JavaScript origin. Set it in `.env` as
`VITE_GOOGLE_CLIENT_ID` — this must be the **same** client ID your backend's
`aquatrack.google.client-id` is configured with, since the backend verifies the token's
audience against it.

## Endpoint map (frontend → backend)

Every network call in this frontend, so you can cross-check it against your controllers:

| Page | Calls |
|---|---|
| Login | `POST /auth/login`, `POST /auth/google/login`, `POST /auth/google/register`, `GET /public/apartments` |
| Register | `POST /auth/register`, `GET /public/apartments`, `GET /public/apartments/{id}/households/lookup` |
| Resident Dashboard | `GET /resident/households/{id}/usage-logs/recent`, `.../invoices`, `.../alerts`, `.../peer-comparison`, `.../fines`, `GET /resident/invoices/{id}/pdf` |
| Admin — Overview | `GET /admin/apartments/{id}/households`, `.../alerts`, `.../usage-comparison`, `.../pending-residents` |
| Admin — Households | `GET .../households/detail`, `POST /admin/households`, `POST /admin/fines` |
| Admin — Pending Approvals | `GET .../pending-residents`, `POST /admin/residents/{id}/approve`, `POST /admin/residents/{id}/reject` |
| Admin — Meter Uploads | `POST /admin/usage-logs/bulk-upload` (multipart), `POST /admin/usage-logs` |
| Admin — Tariff Plans | `POST /admin/tariff-plans`, `GET /admin/tariff-plans/apartment/{id}` |
| Admin — Billing Cycles | `POST /admin/billing-cycles`, `POST .../purchases`, `GET .../purchases`, `GET .../invoices`, `POST .../finalize`, `POST .../archive`, `POST /admin/invoices/{id}/adjustments` |
| Admin — Fines | `GET /admin/apartments/{id}/fines`, `POST /admin/fines/{id}/status` |
| Admin — Alerts | `GET /admin/apartments/{id}/alerts`, `POST /admin/alerts/run-check`, `POST /admin/alerts/{id}/resolve` |
| Admin — Apartment Settings | `PUT /admin/apartments/{id}`, `DELETE /admin/apartments/{id}` |

## Known gaps / things to decide

- **Landing page's "Raise a Query" contact form** has no backend endpoint yet — it still shows
  a simulated success state client-side. Say the word if you want a real
  `POST /api/public/contact` endpoint + email notification added to match.
- **Old resident manual-reading entry is gone** by design (matching your backend, which made
  meter logging admin-only) — the Figma design's `MeterUploadsTab` already only appears in
  `AdminConsole`, so this needed no change.
- I didn't add automated tests for this frontend — say the word if you'd like a starter Vitest
  + React Testing Library setup.
